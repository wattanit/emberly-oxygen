## 1. System layout

A Cargo workspace with two packages: the engine is a library any Rust program can use, and the command-line tool is one consumer of it.

```
emberly-oxygen/             workspace root
  Cargo.toml                workspace manifest
  crates/
    oxygen/                 package `emberly-oxygen` (library)
      src/
        lib.rs
        tensor.rs           tensor type (§3)
        ops.rs              math kernels (§4)
        pool.rs             worker threads for the products and attention (§2, §4)
        config.rs           model configuration (§3)
        safetensors.rs      safetensors reading (§5)
        weights.rs          named weights and their checks (§5)
        model.rs            a loaded model (§3)
        tokenizer/          byte-level BPE encode/decode and streaming (§6)
        forward.rs          transformer forward pass, one token and a batch (§7)
        kv_cache.rs         key-value cache (§3)
        generate.rs         generation and streaming (§8)
        sampling.rs         sampling controls and the sampler (§8)
        chat.rs             chat template and conversations (§8)
        rng.rs              seeded random number generator (§8)
        error.rs            the error type (§14)
        fault.rs            negative-control faults (§17)
      tests/                correctness harness (§11)
      benches/              benchmark harness (§12)
    oxygen-cli/             package `emberly-oxygen-cli` (binary `emberly-oxygen`)
      src/
        main.rs             entry point: run the command, map errors to exit codes
        cli.rs              argument definitions, the generate and chat commands (§9)
      tests/                command-line tests (§9)
  oracle/                   Python reference oracle, including the sampling and chat references (§10)
  fixtures/                 expected outputs, git-ignored, one folder per model
  models/                   downloaded model files, git-ignored
  results/                  cumulative benchmark record (§12)
  docs/                     this suite and release notes
```

- The library package is `emberly-oxygen` (Requirements §12) and has no command-line dependencies. The CLI uses only its public API, so anything the CLI does, another program can do.
- The binary is named `emberly-oxygen` (Requirements §12). Its package is `emberly-oxygen-cli`, because two packages in one workspace cannot share a name.
- The CLI holds no engine logic, so the harnesses test the library directly and still cover exactly what the binary runs.

## 2. Execution model

- **Synchronous, with a pool of worker threads (FR-43, FR-44).** One request, one sequence, no async runtime: a call returns when its work is done. The matrix products and the attention hand their work to a pool of workers made once when the model loads, from the thread count; everything else (normalization, RoPE, SiLU, the elementwise operations, sampling, tokenization, capture, logging) stays on the calling thread. The count defaults to the release's sweep choice, 12 on the benchmark machine for release 0.4.2 (8 for 0.4.1; §12), or the cores the machine makes available when there are fewer and 1 makes no workers at all, so every call runs on the calling thread, which is the 0.4.0 engine. `Model::load` takes the default; `Model::load_with_threads(dir, n)` takes a count, and 0 is rejected as a rejected request naming `threads` (FR-44, §14). The recommendation is to keep the count at or below the machine's performance cores: the default, 12, is the benchmark machine's number of performance cores, and the sweep's 16 threads, which add its 4 efficiency cores, is slower than 12 because every divided product waits for its slowest thread. The default is capped at the cores available and cannot tell performance cores from efficiency cores (the standard library does not say), so on another machine `--threads` should be set to its performance cores. A model's pool serves one call at a time: several sessions at once stay out of scope (Requirements §2.3). Dropping the model stops and joins its workers.
- **The prompt goes through one batched pass; decoding goes one token at a time.** The prompt's tokens are processed together by `prefill` (§7), which leaves the cache filled and returns the logits of the last position (FR-40); every token after the first is generated by the one-token `step` as before. Two code paths mean two things to verify, so the harness judges the batched one (§11) and a test holds the two to each other (§17). `prefill` is called only on an empty cache, as every caller does (generation and a chat turn both start empty); extending a cache that already holds positions is the cache reuse Requirements §2.2 defers, and nothing is shaped for it.
- **Past keys and values are cached.** Each layer stores the key and value vectors of every processed position, so each new token computes only its own row. Recomputing the whole prefix per token would make the 512-token benchmark prompt (§12) quadratically slow and teaches nothing the cache does not; the cache is part of the baseline, not an optimization.
- **Chat processes the whole conversation every turn.** A turn renders the full history (FR-35) and feeds all of it through the forward pass from an empty cache, so a turn's time grows with the conversation. Reusing the cache of earlier turns would be faster and is a technique of its own: it changes what is fed to the forward pass, which this release leaves alone: batching makes the same whole-history prompt cheaper and cache reuse would shrink the prompt, and the two are measured as separate releases (FR-35, FR-40, §12).
- **Streaming by callback.** Generation calls a caller-supplied function with each completed piece of text (FR-17), so the CLI prints as tokens arrive and the harnesses collect output without a separate code path.

## 3. Data models

**Tensor.** A contiguous `Vec<f32>` with a shape, row-major. f32 only: weights stored in bfloat16 are widened to f32 at load, which is exact, so engine and oracle compute from identical values (FR-2).

**Model configuration.** Parsed from the model's `config.json`. The supported set is checked at load and anything else is rejected naming the field (FR-12):

| Field | Supported value |
| --- | --- |
| `model_type` | `llama` |
| `hidden_act` | `silu` |
| `attention_bias`, `mlp_bias` | `false` |
| `rope_scaling` | `null` |
| `rope_interleaved` | `false` or absent (half-split pairing) |
| `tie_word_embeddings` | `true` |
| `pretraining_tp` | `1` or absent |
| `eos_token_id` | one whole number inside the vocabulary (some models list several; any other form is rejected as unsupported naming the field, an ID outside the vocabulary as malformed) |

Sizes (hidden size, layers, heads, key-value heads, head dimension, intermediate size, vocabulary, context length), `rope_theta` and `rms_norm_eps` are read from the file, not hard-coded, so a model with the same architecture but different sizes needs no code change.

**The instruct variant (FR-32).** Compared on 2026-11-08 at revision `12fd25f77366fa6b3b4b768ec3050bf629380bac` of SmolLM2-135M-Instruct against the base model's files: its `tokenizer.json` is equal to the base model's as JSON, and its `config.json` differs only in `bos_token_id` (1), `eos_token_id` (2), `pad_token_id` (2), an explicit `mlp_bias: false` and metadata. The engine reads `eos_token_id` and not the other two, so the supported set above and the loader are unchanged and the model loads with no instruct-specific code. The end-of-sequence token being `<|im_end|>` is all that makes generation stop at the end of a chat turn (FR-34, §8). A test pins these facts against the real files, so a revision that differed would be rejected under FR-12, not run.

**Weights.** Token embedding table (also used as the output projection, because embeddings are tied); per layer: attention norm, query, key, value and output projections, MLP norm, gate, up and down projections; final norm. Matrices keep their published `[out, in]` layout, so each output element is a dot product over one contiguous row, and no conversion step exists (FR-11).

**Key-value cache.** Per layer, one growing `Vec<f32>` for keys and one for values, each laid out `[position][kv_heads × head_dim]`. Appending a position is a single extend; reading position `t` is a contiguous slice.

**Tokens.** Token IDs are `u32`.

## 4. Tensor operations and kernels

The operation set is exactly what the forward pass needs: matrix-vector product, RMSNorm, softmax, rotary position embedding (RoPE), SiLU, elementwise add and multiply. Each is a plain loop over slices with f32 accumulation in index order, except the matrix-vector product (below). None uses `unsafe` or SIMD intrinsics (HC-1, FR-25); the products and the attention use the pool (below, FR-43). The other operations stay plain, one row at a time: the matrix-vector product was about 94% of a step in release 0.1.0 and, after the partial sums, is about 86% of a short step and 58% of a long one (release note 0.1.1, estimated from the kernel rows). On long prompts the rest, mostly attention over the cache, is therefore a real share, about 42%. The profile of 2026-11-11 (plan 0.4.1 §5) puts a decode step at 7.7 ms with 8 tokens of context, 11.3 ms at 512 and 24.1 ms at 2000, of which the matrix-vector products are 7.2 ms, so attention is about a third of a step at 512 positions and two thirds at 2000; that is why 0.4.1 threads it as well as the products (decided by the owner, 2026-11-11).

- **Matrix-vector product.** Output element `i` is the dot product of weight row `i` with the input, matching the `[out, in]` layout (§3). The dot product keeps 16 independent f32 partial sums (FR-25): sum `j` adds the elements whose index is `j` modulo 16, each in index order; the 16 sums are then added to one another sequentially from sum 0, and the final `in mod 16` elements are added in index order after them. The count of 16 was chosen in release 0.1.1 by a sweep of 4, 8, 16 and 32 sums, with the rule fixed before measuring: the lowest estimated kernel time per token, ties within 2% going to the smaller width. It beat 8 sums by about 20% and 32 sums everywhere; it remains tunable with use. Index-order addition was a chain of dependent adds, each waiting for the last, so the processor could not overlap them; independent sums remove the wait and let the compiler use vector registers, from safe code alone. Release 0.1.1 measured the kernel at 6.4× to 8.3× the index-order loop at the model's five shapes.
- **Prohibited in the kernel, for now.** `unsafe`, SIMD intrinsics and weights at lower precision stay out (Requirements §2.2), and so does any parallelism crate (HC-1): each is its own technique and is measured as its own release. Register tiling of the batched product is the exception that release 0.4.2 adds (FR-46, below); the matrix-vector product stays untiled. If safe code does not vectorize as expected, or cannot hand the workers what they read (§19), the implementation raises the issue with the owner instead of reaching for `unsafe`.
- **Matrix-matrix product (FR-40).** `matmul(W, X, Y)` computes `Y[t][i] = dot(W row i, X[t])` for `n` input rows. Its loops run weight row outermost and input row innermost, so each weight row is read from memory once and reused for all `n` inputs while it is in cache; the 0.3.0 per-token path reads every weight row once per token, and at 135M parameters in f32 (about 540 MB) the weights far exceed the cache. Each element is the same 16-partial-sum dot product as the matrix-vector product (FR-25), the same function and not a copy, so there is one summation order to reason about. The loop order is the whole technique of the product itself: no block of inputs is held in registers, no weight block is kept resident across tiles, and nothing in its loops is vectorized by hand, because that is tiling and each of those is its own release (Requirements §2.2); threads divide its rows from outside (below, FR-43). If the loop order alone gives little, that is a recorded negative result (FR-42), and the implementation raises it with the owner rather than adding a technique. The arithmetic of every element, and so of every logit, equalled the one-token path's in releases 0.4.0 and 0.4.1 (0.4.2's blocked product, below, gives that up); the requirement does not promise it (FR-41), so a later change to this loop may give up the equality without a requirement changing.
- **Blocked matrix-matrix product (FR-46, FR-47).** `matmul_blocked(W, X, Y)` computes the same `Y[t][i]` as `matmul` in tiles of `MR` weight rows by `NR` input rows, initially 4 × 16 (from the profile; the plan's first kernel task sweeps tile shapes in the engine at the model's shapes and the owner decides; tune with use). The input rows are packed once per call into panels laid out `[k][NR]`, so the inner loop reads `NR` consecutive inputs for each weight value; the weights are read in place in their published layout, with no packed copy and so no extra memory. The inner loop adds `w[i][k] * x[k][j]` into an `MR × NR` array of accumulators for `k` from 0 upward with `f32::mul_add`, one fused multiply-add per product, rounded once, for a chunk of `KC` values of `k` (initially 64) at a time, after which the chunk's accumulators are added into the running totals, so each output element is a sum in index order taken in chunks (chunks of fused sums, added in order), and the compiler can vectorize across the `NR` inputs from safe code as it vectorized the 16-sum loop across its sums. The leftover rows (`rows mod MR`) and inputs (`count mod NR`) are summed the same way, one element at a time in index order, so an element's value does not depend on the tile it falls in; that is what lets the pool divide the rows (in ranges of whole `MR` multiples where the size allows) without changing a bit (FR-43). The caller packs the input once and hands the pool a shared copy, as for the other inputs. `prefill` calls it for every projection; the final unembedding of `Logits::Last` and the whole decode step keep `matvec`, and with them their 16 partial sums, so from 0.4.2 a `prefill` and a `step` no longer do the same arithmetic and differ in the last bits (§11). The chunking is for accuracy: with one long sequential sum per element the worst error against the 64-bit reference on the real model rose from 3.50e-4 to 6.51e-4 in logits (65% of S-1) and from 9.97e-6 to 4.53e-5 in relative intermediates (45% of S-2); with chunks of 64 it is 2.72e-4 and 7.98e-6, below 0.4.1's, for about 3% of the kernel's speed (plan 0.4.2 §5). The 0.4.1 loop `matmul` stays in the library as the baseline for the kernel group (§12) and the drift check (§11). Profile (plan 0.4.2 §5, one core, 128 inputs, at the model's three prompt shapes): the current loop reaches 39 GFLOP/s, a safe blocked kernel with a separate multiply and add 65 to 70, the same tile with `mul_add` 118 to 120 at 4 × 16 (115 at 8 × 8 only with the weights also packed, a 540 MB copy that is not taken), and `matrixmultiply`'s sgemm 109 to 115. The compiler's vectorization is fragile: other tile shapes with `mul_add` fell to 16 to 32 GFLOP/s (4 × 8, 8 × 4, 6 × 8, 12 × 4, 8 × 16), so the tile shape is pinned by the benchmark and a kernel-rate row in the record shows a regression (§12). `mul_add` is a hardware instruction on the benchmark machine's architecture (aarch64); on one without hardware fused multiply-add it is a slow library call, and the rate claimed is the benchmark machine's only (Requirements FR-47, S-7).
- **Threaded products (FR-43).** `matvec`, `matmul` and `matmul_blocked` divide the weight's rows into contiguous ranges, one per worker, with sizes that differ by at most one; each output element is computed whole by one worker with the same `dot_lanes` call as before, so no sum is split and the result equals the single-threaded one bit for bit at every thread count. The unit of work is an output element and never a part of a dot product: splitting a dot product across workers would add the partial results in a different order and give up FR-43. A product too small to repay the hand-over runs on the calling thread: below a threshold of multiply-adds (rows × columns × inputs), set from the measured per-call cost of the pool (initially 500,000 multiply-adds; tune with use; the key and value projections, 192 × 576 and 0.18 ms each, are the likeliest to fall below it). The calling thread takes one range itself instead of waiting, so a count of `n` uses `n` threads, not `n + 1`.
- **Threaded attention (FR-43).** Only independent output elements are divided. In a one-token step the query heads are independent, each reading its key-value head's slice of the cache and writing its own `head_dim` slice of the output, so heads are divided among workers with the per-head arithmetic (scores, softmax, weighted sum) unchanged; nine heads bound that split's parallelism at nine workers. Finer splits that stay inside the rule (the score of each position is independent of the others; so is each output dimension of the weighted sum, which sums over positions in order) are for the plan to try if the heads alone do not reach the memory system's rate. In `prefill`, rows are independent (§7), so rows are divided among workers and each row runs the existing single-row function. The softmax's sum over positions is never split. As built (plan 0.4.1 §5): a decode step threads its attention from 256 positions of context (initial; tune with use); the rows of `prefill` are taken in a zigzag order (first row, last row, second row, ...) so every range mixes cheap and dear rows, `t + 1` positions costing more as `t` grows, and are put back in order; the pool wakes no more workers than there are elements; and with the trace level on, the serial attention runs, because it records the most-attended positions, with an equal output.
- **Persistent workers.** The workers are created at model load and wait between calls, because a decode step makes 211 matrix products and 30 attention calls and creating threads for each would be paid that many times per token. Measured before the pool was built (plan 0.4.1 §5, task 20.1): a thread created per call costs about 8 µs per extra thread (122 µs at 16), more than most products, against about 3 µs per extra worker for a persistent one. The pool is built from `std::thread` and the standard library's synchronization, in safe code (FR-43).
- **RMSNorm.** `x · w / sqrt(mean(x²) + eps)`, with `eps` from the configuration.
- **Softmax.** Subtracts the maximum before exponentiating, so large scores cannot overflow.
- **RoPE.** Half-split pairing: dimension `i` rotates with dimension `i + d/2`, at frequency `theta^(-2i/d)`. Frequencies, angles, sines and cosines are computed in f32, not f64, because the reference computes them in f32 and a more precise angle is a different angle.

The engine computes in f32 and the reference in f64, so engine results differ from the reference in the last bits of f32 rounding, which depends on the order of additions; S-1 and S-2 bound that difference. The partial sums also make the engine's logits differ in the last bits from release 0.1.0's, which were summed in index order; they are still bit-identical from run to run on one machine, because the number of sums and the combining order are fixed (S-6), and from 0.4.1 also at every thread count (FR-43). Release 0.1.1 is therefore compared with 0.1.0 by the harness thresholds and by speed, never by exact equality. Decoded argmax tokens are protected only by S-3 and S-4, whose near-tie rule exists for exactly this reason.

## 5. Model loading

A model is a directory holding `config.json`, a single `model.safetensors` and `tokenizer.json`, exactly as published (FR-11).

- **Format.** The safetensors file is read in-house (HC-1): an 8-byte little-endian header length, a JSON header mapping each tensor name to dtype, shape and byte range, then raw data. The file is memory-mapped and each tensor copied into an owned f32 tensor.
- **Dtypes.** F32 is copied; BF16 is widened to F32, which is exact. Any other dtype is rejected naming the tensor and dtype (FR-12).
- **Names.** Tensors are found by their published names (`model.embed_tokens.weight`, `model.layers.{i}.self_attn.q_proj.weight`, and so on). A missing tensor, a tensor whose shape disagrees with the configuration, or an unexpected tensor is rejected naming it, because any of these means the file is not the model the configuration describes.
- **Not supported:** weights split across several files. SmolLM2-135M ships as one file; sharding is rejected with an error.

## 6. Tokenizer

The tokenizer is byte-level BPE, read from `tokenizer.json` and implemented in-house (HC-1).

- **Encoding.** Special tokens are matched first. The remaining text is split by the pre-tokenizer that `tokenizer.json` declares, each piece's bytes are mapped to the byte-level alphabet, and BPE merges are applied lowest rank first until no ranked pair remains. Pieces then map to IDs. The splitting pattern is hand-written rather than run through a regex crate: the standard byte-level pattern uses lookahead, which Rust's `regex` crate does not support, and hand-writing it is part of the point.
- **Components.** Only the types SmolLM2's `tokenizer.json` actually uses are implemented, and anything else is rejected as an unsupported component naming it (plan 0.1.0 task 3.6). The file declares: model `BPE` with no dropout, unknown token, subword prefix or suffix, byte fallback or `ignore_merges`; normalizer none; pre-tokenizer a sequence of `Digits{individual_digits: true}` then `ByteLevel{add_prefix_space: false, use_regex: true}`; post-processor none, so no beginning-of-sequence token is added and the reference's encoding carries none; decoder `ByteLevel`; no truncation or padding. The vocabulary has 49152 entries and 48900 merges, and 17 added tokens at IDs 0 to 16, all special and all also in the vocabulary (`<|endoftext|>` is ID 0, also the end-of-sequence ID). The engine requires vocabulary IDs to be exactly 0 to n-1 and added tokens to appear in the vocabulary under the same ID. A test pins these facts against the real file (FR-13).
- **Chat markers (FR-33).** In the instruct model's `tokenizer.json`, which has the same 17 added tokens as the base model's, `<|im_start|>` is ID 1 and `<|im_end|>` ID 2; both are special, so they are matched literally before splitting and encode as one token each, with no change to the tokenizer. The same holds for any text containing their spelling, typed by a user or generated by the model: it becomes the marker token, as in the reference. The engine does not escape them, because S-11 requires the rendered text to encode exactly as the reference's does; the consequence is that a user message containing `<|im_end|>` ends its turn early, as it does in the reference (FR-33, decided by the owner).
- **Character classes are measured, not borrowed.** Letter, number and white-space ranges for the splitting pattern come from `oracle/unicode_classes.py`, which runs every Unicode scalar value through the reference pre-tokenizer and writes `tokenizer/unicode_classes.rs`, a committed file. Rust's `char::is_alphabetic` is not Unicode `\p{L}` (it counts some Thai vowel signs as letters), and a different Unicode version would shift piece boundaries silently; swapping it in made 557 of 3,979 corpus cases fail. A second oracle output, `oracle/tokenizer_corpus.py`, stores the reference's pieces and token IDs for about 4,000 strings, and the tokenizer tests compare against it.
- **Bytes with no vocabulary entry are dropped silently.** SmolLM2's vocabulary has no entry for 21 of the 256 byte-level characters (bytes 4, 6, 19, 20, 22, 29, 192, 193, 241, 242 and 245 to 255), and the reference drops them, so `"a\x04b"` encodes as `a` and `b` only. The engine does the same because FR-13 requires exact agreement. This is a known loss, not a guarantee of fidelity; whether it should warn or reject is an Open Question of the Requirements.
- **Decoding.** IDs map to piece strings, then back to bytes through the inverse byte map (FR-14). As the oracle decodes (`AutoTokenizer.decode`, default options): special tokens are kept and print as their text, no tokenization-space cleanup is applied, the bytes of all tokens are joined before being read as UTF-8 (so a character split across tokens decodes whole), and bytes forming no valid sequence become U+FFFD, one per maximal invalid subsequence, the same rule as `String::from_utf8_lossy`. A character outside the byte-level alphabet stands for no byte and is skipped. An ID outside the vocabulary is a rejected request.
- **Streaming decoder.** Decoded bytes accumulate in a buffer. After each token, the longest valid UTF-8 prefix is emitted and a trailing incomplete sequence of up to 3 bytes is held back (FR-15). Bytes that cannot begin or continue a valid sequence become U+FFFD, as the reference's decode does; at end of generation the held bytes are flushed the same way.

## 7. Forward pass

One call processes one token at position `p` and returns logits over the vocabulary.

1. `x` = embedding row of the token.
2. For each layer:
   1. `h` = RMSNorm(`x`, attention norm weight).
   2. Query, key and value = their projections of `h`; RoPE at position `p` is applied to query and key.
   3. Key and value are appended to this layer's cache.
   4. Each query head attends over cached positions `0..=p` of its key-value head (head index divided by the group size, the number of query heads per key-value head): scores are dot products scaled by `1/sqrt(head_dim)`, softmax, then a weighted sum of values.
   5. `x` += output projection of the concatenated heads.
   6. `h` = RMSNorm(`x`, MLP norm weight); `x` += down(SiLU(gate(`h`)) × up(`h`)).
3. Logits = embedding table × RMSNorm(`x`, final norm weight), using the tied embeddings.

The residual stream `x` is never normalized in place; only the copies fed into attention, the MLP and the output are. An optional capture records `x` after the embedding and after each layer for the correctness harness (FR-1, FR-6); it is off in normal runs.

**Batched prompt pass (FR-40, FR-41).** `prefill(tokens, logits, capture)` processes `n` prompt tokens at positions `0..n` of an empty cache. Activations are `[n, width]` row-major matrices, one row per token, in the same layout the cache uses for its positions (§3).

1. `X` = the embedding rows of the tokens. Every token is checked against the vocabulary and the cache against the context length before anything is touched, so a rejected call leaves the cache and the capture as they were, as `step` does.
2. For each layer, the same six operations as the one-token pass, each over all rows: RMSNorm of each row; query, key and value by `matmul` (§4); RoPE of row `t` at position `t`; all `n` keys and values appended to the cache; attention; the output projection by `matmul`, added to `X`; RMSNorm, gate and up by `matmul`, SiLU and multiply, down by `matmul`, added to `X`.
3. **The causal mask is a count, not a matrix.** Row `t` attends to cache positions `0..=t` by calling the existing `attention` function with `t + 1` positions, so no position sees a later one and no `n × n` score matrix is built. The keys and values of the whole prompt are appended before attention runs, which is why the count is what keeps the future out: reading beyond it would be reading the later prompt tokens. `attention` itself is not batched or changed; it was about 42% of a long step (§4) and whether to speed it is a later release's decision.
4. **Logits.** `Logits::Last` (generation, chat) applies the final norm and the unembedding by `matvec` to the last row only; `Logits::All` (the harness, S-1 and S-3 at every position) applies them to every row by `matmul` and returns `[n, vocab]`. The one-token path computed the unembedding, 17% of a token's work (1.6 ms of a 9.7 ms step, plan 0.4.0 §5), at every prompt position and used only the last; skipping it is part of what this release changes beside the batching. `Logits::All` for a 2048-token prompt is about 400 MB, which is why only the harness asks for it and no caller keeps it.
5. **No chunking.** The whole prompt is one pass, with the largest activation matrix `n × intermediate_size` (12 MB at 2048 tokens), so splitting a prompt to bound memory is not needed and not built; a prompt is already limited by the context length (FR-18).
6. `capture` records `X` after the embedding and after each layer as `[n, hidden]` tensors, the shape the stored intermediates have (§11), and the final-norm output for all rows when `Logits::All`.

The one-token `step` is unchanged and still computes and returns logits for its token. A `Fault` (§17) is applied in `prefill` as in `step`, so the negative controls run through the batched pass.

## 8. Generation

1. Encode the prompt. Reject it before any computation if the prompt is empty or prompt length plus maximum new tokens exceeds `max_position_embeddings` (FR-18).
2. Process the prompt in one batched pass, `prefill` with `Logits::Last` (§7, FR-40); its logits are the first step's, so step 3 chooses from them. Every later token is fed through `step` as before.
3. Choose the next token. With greedy settings (below), take the highest logit; on an exact tie, the lowest ID wins, as the reference's argmax does (FR-16). Otherwise sample (below, FR-26).
4. If the token is the configuration's `eos_token_id`, stop; the token is returned among the generated IDs, because the oracle's continuation includes it and S-4 compares IDs, but its text is not passed to the callback, since standard output is generated text and the end-of-sequence token is a control signal (FR-17, FR-20).
5. Otherwise pass the token to the streaming decoder and emit any completed text to the callback (FR-17). Stop after the maximum number of new tokens; flush the decoder.

**Sampling (FR-26 to FR-29).** `generate_with` takes a `Sampling { temperature, top_k, top_p, repetition_penalty, seed }`; its default is greedy. `generate` keeps its signature and is the greedy case, a call of `generate_with` with the default, so every existing caller and the greedy harness are untouched and a caller that passes nothing gets the 0.1.2 behavior (FR-29). With sampling on, `generate_with` requires a seed and rejects the request naming it, so a run can always be replayed (FR-28). The settings are validated before any computation and an invalid value is rejected as a rejected request naming the option and the value (FR-30, §14): temperature finite and at least 0, top-k at least 0, top-p greater than 0 and at most 1, penalty greater than 0.

- **Neutral values.** Temperature 0 is greedy selection; top-k 0, top-p 1 and penalty 1 change nothing. The default is temperature 0, so with no sampling option set generation is greedy (FR-29).
- **Temperature 0 ignores the other controls.** Greedy selection takes the argmax of the raw logits, so the output is the previous release's greedy output whatever else is set (FR-29); if another control is not neutral, a warning says it was ignored, so a setting that does nothing is never silent.
- **Order, per step (FR-26).** On a copy of the step's f32 logits: (1) repetition penalty (FR-27): for each distinct token already in the context, prompt and generated, a positive logit is divided by the penalty and a negative one multiplied by it; (2) divide every logit by the temperature; (3) top-k: tokens whose logit is below the k-th highest are removed, so tokens tied with the k-th are kept, as the reference does; (4) top-p: the probabilities (softmax of what remains) are sorted ascending and a token is removed when the running sum up to and including it is at most 1 − p, which keeps the smallest set of highest-probability tokens whose sum is at least p, and always keeps at least one token; then (5) the distribution is the softmax of the remaining logits, and one token is drawn from it.
- **Arithmetic.** The controls run in f32, as the logits are. The softmax, the cumulative sum and the draw run in f64, because the final probabilities are compared with an f64 reference (S-9) and 49152 terms are cheap to sum exactly enough. The distribution is a public function of the logits, the context and the settings, so the harness can compare it with the stored one (FR-31, S-9) without drawing.
- **The draw.** The random number generator is xoshiro256**, seeded from the 64-bit seed by SplitMix64, written in this project (HC-1: no `rand` crate, because the generator is part of what the project exists to understand). It produces a uniform f64 from the top 53 bits of one output. One draw is consumed per sampled token and none for a greedy one, so the number of draws never depends on logging (S-8). The chosen token is the first whose cumulative probability, summed in token-ID order, exceeds the draw. The algorithm is the Specification's choice: Requirements FR-28 promises reproduction within a build only, so a later release may replace it.
- **The seed.** When sampling and no seed is given, the CLI takes one from the system clock, and it always prints `seed: <n>` to standard error (FR-20) before any text, so the run can be replayed (FR-28). `Generation` carries the seed used, `None` for greedy generation.
- The last generated token is not fed back through the forward pass, since nothing would use its logits; the context check in step 1 still counts it (FR-18). A maximum of zero new tokens is allowed: the prompt is checked and nothing is computed.
- `generate` returns `Generation { ids, stats }`. `Stats` holds the prompt and generated token counts, time to first token and generation time, with the two throughputs as methods. The CLI may use only the public API (§1), and time to first token cannot be seen through the text callback (the first token may complete no text, or be end-of-sequence), so the library reports it. Time to first token runs from receiving the prompt string, so it includes encoding, to choosing the first token. The first generated token's cost counts as prompt work, and now the pass that produces it is the batched one: prompt throughput is prompt tokens over that time, and generation throughput is the tokens after the first over the time after it, absent for a single token (FR-8, FR-21).

**Chat (FR-33 to FR-37).** `chat.rs` holds the template and the conversation and adds no arithmetic: it builds prompts and calls the generation path above.

- **Template.** `Role` (system, user, assistant) and `Message { role, content }`. `render(&[Message], add_generation_prompt) -> String` is a transcription of the template published in the instruct model's `tokenizer_config.json`: if the first message is not a system message, `<|im_start|>system\nYou are a helpful AI assistant named SmolLM, trained by Hugging Face<|im_end|>\n` comes first; each message is `<|im_start|>`, the lowercase role, a newline, the content unchanged, `<|im_end|>` and a newline; and with `add_generation_prompt`, `<|im_start|>assistant\n` ends the text. A system message anywhere but first is rendered as given, as the template does. The template is written in Rust, not interpreted: a Jinja interpreter is either a dependency that does template work (HC-1 allows general plumbing only, §15) or a large piece of code for one three-line template, and the question returns with the Qwen chat template (roadmap v6), when two templates differ for real. Content is inserted verbatim with no escaping (§6). The rendered text is encoded by the tokenizer, which turns each marker into its token (§6, FR-33).
- **Conversation.** `Chat::new(model, tokenizer, system, &Sampling, max_new_tokens)` validates the settings and requires a seed when sampling, as `generate_with` does (FR-30, FR-28), and holds the messages (the system message first when given) and one random number generator built from the seed once. `Chat::turn(user, on_text)` renders the messages plus the new user message with the generation prompt, generates from that text with the same step loop and the conversation's generator, which carries on from where the last turn left it (FR-37), and streams text to `on_text`. Only when generation succeeds does it append the user message and an assistant message holding the text streamed, which is the reply as the user saw it (FR-35); on any error the messages are as before (FR-36). Rejection is the check of step 1 on the rendered prompt's token count plus the maximum new tokens, so it happens before any computation (FR-18, FR-36).
- **A reply.** Generation stops at `eos_token_id`, which for the instruct model is `<|im_end|>` (§3), or at the maximum; the end token is not streamed (§8 step 4, FR-34). The stored assistant message carries no end marker either way, because the template adds `<|im_end|>` and a newline when it renders the message, so a reply cut by the maximum is closed in the next prompt (FR-34).
- **Repetition penalty in chat** takes the rendered prompt of the turn, history and system message included, and the tokens generated so far in the turn as its context (FR-27), the same rule as a prompt in `generate_with`.
- **Greedy is untouched.** `generate` and `generate_with` do not change (FR-29); `chat` is a separate path over the same loop.
- Not guaranteed: replies are stored as text and encoded again each turn (FR-35), so a reply whose text encodes to different tokens than were generated conditions later turns on the encoded ones. The reference does the same, which is why this is kept.

## 9. Command-line interface

```
emberly-oxygen generate --model <dir> --max-new-tokens <n> [--temperature <t>] [--top-k <k>] [--top-p <p>] [--repetition-penalty <r>] [--seed <n>] [--threads <n>] [--stats] [-v|-vv|-vvv] [--log-file <path>] [PROMPT]
```

- The prompt is read from standard input when no argument is given (FR-19).
- The chat command is described after the generate command's options, below.
- The four sampling options and `--seed` map onto `Sampling` (§8, FR-30); each defaults to its neutral value, and the library rejects an invalid value, so the exit code is 1 and the message names the option and the value (§14). A value that is not a number of the option's type (text, or a negative `--top-k` or `--seed`) is rejected by the argument parser instead, as a usage error with exit code 2 that also names the option and the value.
- `--threads` maps onto the thread count (§2, FR-44) for both commands and defaults to the sweep's choice, 12, or the cores available when fewer; it is recommended not to exceed the machine's performance cores (§2). The library rejects 0, so the exit code is 1 and the message names the option and the value (§14); a value that is not a whole number is rejected by the argument parser, as a usage error with exit code 2.
- Generated text goes to standard output and nothing else; errors go to standard error with a non-zero exit code (FR-20).
- `--stats` prints, to standard error, the model load time (timed by the CLI around both loads) followed by prompt token count, generated token count, time to first token and generation tokens per second, defined as in §8 (FR-21).
- A write error on standard output, such as a reader closing the pipe, makes the text callback exit with code 1, so generation stops at once instead of running to the maximum (FR-20). The CLI package's own tests run the built binary and check FR-19 to FR-21.

```
emberly-oxygen chat --model <dir> [--system <text>] [--max-new-tokens <n>] [--temperature <t>] [--top-k <k>] [--top-p <p>] [--repetition-penalty <r>] [--seed <n>] [--threads <n>] [-v|-vv|-vvv] [--log-file <path>]
```

- **Chat mode (FR-38).** It loads the model once, builds a `Chat` (§8) and loops: write the marker `> ` to standard error, read a line from standard input, and stop at end of input, after a newline on standard error so the shell's prompt does not start after the last marker, or at a line that is exactly `/exit`; a blank line is skipped and sent nowhere. Each other line is one user message. The reply streams to standard output as it is produced, and the command writes a newline after each reply so that replies stay apart; that newline and the reply text are all that standard output holds (FR-20). A rejected turn (§14) prints its error to standard error and the loop continues with the conversation as it was; any other error ends the command with exit code 1 (§14). End of input or `/exit` exits with code 0.
- **Defaults (FR-37).** `--max-new-tokens` defaults to 256 (initial; tune with use), `--temperature` to 0.2 and `--top-p` to 0.9, the model card's values; the other sampling options keep their neutral defaults. When `--temperature 0` is given and `--top-p` is not, top-p is taken as 1, so asking for greedy chat is not answered with a warning about a control the user never set; a control the user did set is still reported ignored (§8). When the settings sample and no `--seed` is given, the seed comes from the system clock and `seed: <n>` is written once to standard error before the first prompt marker (FR-28). `--system` replaces the default system message.
- `-v` levels and `--log-file` behave as for the generate command (FR-23, FR-24); a step event's `next` and probability fields (§14) are logged per turn.

## 10. Reference oracle

The oracle lives in `oracle/`, a Python project managed by `uv` with a lockfile pinning `torch`, `transformers` and `huggingface_hub`, so expected outputs can be regenerated with the same library versions.

- **Model revision.** The model is downloaded at a pinned commit of its repository; the same files are the engine's model directory, so both read identical bytes (FR-11). The download script is the only step that needs network access.
- **Settings.** Two runs on CPU, in f64 and in f32 (FR-2), each loaded from the same published weights (bfloat16 widened exactly, as the engine widens them), with eager attention so no fused kernel changes the arithmetic, and gradients disabled. The oracle asserts each model's parameter dtype and device before running. In the f64 run the oracle forces the two operations the library computes in 32-bit inside any model to run in the model's dtype: RMSNorm (the library casts its input to 32-bit, normalizes and casts back) and the attention softmax (the library passes `dtype=torch.float32`). They are replaced for the duration of that run only, by a context manager that restores the library afterwards, so the f32 run is the unmodified library. Before the f64 run the oracle checks the replacement is active: a float64 RMSNorm of an input that 32-bit rounding would change must match a float64 calculation to 1e-14, and the softmax of a float64 tensor must come back as float64. The rotary tables are not replaced (below). The f64 run is the reference of S-1 to S-4; the f32 run is the library's default precision, kept so the harness can report the engine's distance to it (FR-5, §11) and the disagreement between the two references stays visible.
- **Prompt set.** `oracle/prompts.json` lists each prompt with an ID and a category: `english`, `thai`, `code`, `utf8-split` (prompts whose tokens split multi-byte characters) and `long` (about 512 tokens, the longest benchmark prompt, §12). Each category has at least two prompts (FR-3).
- **Greedy continuation.** 32 tokens per run, produced by the oracle's own argmax loop rather than a library generate call, so it can record the gap between the two highest logits at every step for near-tie detection (S-3, S-4). Each run continues from its own tokens, so the two continuations agree until a step whose gap is small enough for rounding to flip the choice, and may differ after it.
- **Output.** `fixtures/<model-id>/manifest.json` records the model ID and commit, library versions, the generating machine, and per prompt: ID, category, text, token IDs, continuation IDs and text, and top-two gaps. Each prompt has two safetensors files with the same tensor names and shapes: `<id>.safetensors` (f32, the 32-bit run) and `<id>.f64.safetensors` (f64, the reference, stored in 64-bit so the reference is not rounded to 32-bit again). Each holds logits `[positions, vocab]`, embeddings `[positions, hidden]`, layer outputs `[layers, positions, hidden]` and `final_norm_output` (FR-1). The manifest keeps the existing per-prompt fields for the 32-bit run and adds, for the reference, its file name, continuation IDs and text, whether it stopped at the end-of-sequence token, and top-two gaps at the prompt positions and the continuation, all prefixed `f64_`. Fixtures are model-agnostic in shape, so adding a model adds a folder (Requirements §2.2).
- **Honesty note.** In the reference library, the last entry of the library's hidden states is taken after the final norm, not straight from the last layer. The oracle therefore captures every layer's raw output with forward hooks (checked equal to the library's own hidden states for all other layers) and stores the final-norm output separately as `final_norm_output`; the harness compares that against the engine's normalized output.
- **Top-two gaps** are stored for the prompt positions as well as for the continuation, because the near-tie test of S-3 applies at every position. S-3 and S-4 use the f64 gaps.
- **The reference's own limits.** The library computes its rotary sines and cosines in f32 even in a f64 model (it casts the angles to f32 and the results back, in the pinned version), and they are left as the library makes them: they are the model as published, so the f64 reference shares the engine's f32 RoPE tables (§4), where a true f64 angle would be a different angle (at position 5000 its cosine differs by 8.4e-5). The reference is independent of the engine but not of the reference library: it carries that library's definition of the model, including the f32 rotary tables. Measured in plan 0.1.2: the library's unmodified f64 run changed by up to 1.7e-5 in logits with the thread count and differs by up to 7.3e-5 from the run with RMSNorm and softmax in 64-bit, which is why the oracle makes that replacement; with it, a rerun at another thread count differs by about 2e-6 in logits. Any residual noise is measured again whenever the oracle's library versions change.
- **Sampling reference (FR-31).** `oracle/sampling_reference.py` reads the f64 fixtures already stored, so it does not rerun the model. For each prompt and each setting in `oracle/sampling_settings.json` it takes the f64 logits at the prompt's last position and the prompt's token IDs, applies the reference library's `RepetitionPenaltyLogitsProcessor`, `TemperatureLogitsWarper`, `TopKLogitsWarper` and `TopPLogitsWarper` in the order of §8, and writes the softmax in f64 as `<id>.sampling.safetensors` (one vocabulary-sized f64 tensor per setting). It checks first that the processors keep f64 (the same kind of start-up check as the model's, shown to fail if a processor narrowed). The manifest gains a `sampling` entry listing the settings and, per setting, the smallest margin to a cutoff (the gap between the k-th and the next logit for top-k; the probability just above and below p for top-p), so the harness can tell a cutoff the engine's rounding might cross. The settings file holds each control alone and one combination: a temperature below 1, a top-k, a top-p, a penalty above 1, and all four together (initial; tune with use). Each distribution is about 0.4 MB, so the 60 of the prompt set are about 23 MB.
- **Chat reference (FR-39).** `oracle/conversations.json` lists four conversations by ID: `no-system`, `with-system`, `multi-turn` (three user turns with the assistant's earlier replies written into the messages) and `thai`. `oracle/chat_reference.py` runs on the instruct model, `smollm2-135m-instruct`, downloaded by `oracle/download.py` (which takes a model argument: repository and pinned revision per model, the base model's unchanged, the instruct model at the revision of §3). The instruct download also fetches `tokenizer_config.json`, which holds the chat template and which only the oracle reads; the model directory the engine loads stays the three files of §5. For each conversation it renders the library's template (`apply_chat_template` with `tokenize=False` and the generation prompt), encodes the rendered text by calling the tokenizer without added special tokens (the instruct `tokenizer.json` has no post-processor, so this equals the engine's encoding; the script asserts it equals `apply_chat_template` with `tokenize=True`), then runs the model in f64 exactly as §10's f64 run does (the same context manager and start-up check, imported from the shared module, not copied) and stores the logits at every prompt position and a greedy reply of up to 64 tokens from the oracle's own argmax loop, stopping after `<|im_end|>`, with the top-two gaps at the prompt positions and the reply steps (initial; tune with use). The 32-bit run and the intermediates are not produced: FR-39 asks for logits and replies, and the 32-bit distance is reported for the base model only (FR-5). Output is `fixtures/smollm2-135m-instruct/chat.json` (model ID and commit, library versions, machine, and per conversation: ID, messages, rendered text, token IDs, reply IDs and text, whether it stopped at `<|im_end|>`, gaps, and the file name) and one `<id>.f64.safetensors` per conversation holding `logits`. That folder has no `manifest.json`, so the manifest discovery of §11 passes over it and S-1 to S-4 never judge the instruct model (Requirements §13); the chat checks read `chat.json`. The four conversations are 29 to 110 positions and each position is 0.39 MB in f64 (49152 logits of 8 bytes), so the folder is about 100 MB.
- **Further outputs.** `oracle/tokenizer_corpus.py` writes `fixtures/<model-id>/tokenizer-corpus.json` (§6), `oracle/unicode_classes.py` writes the committed character classes (§6), and `oracle/rope_reference.py` prints the reference's rotary cosines and sines at positions 1 and 5000 as Rust constants for the RoPE test, because f32 angles must agree with the reference's (§4): at position 5000 an f64 cosine differs from the reference's by 8.4e-5.

Logits dominate fixture size: about 200 KB per position in f32 and twice that in f64, so a long prompt is about 100 MB in f32 and about 200 MB in f64, and the fixtures folder grows from about 0.7 GB to about 2 GB. Fixtures are therefore kept out of git: \`fixtures/\` is git-ignored and filled by running the oracle locally. What regenerates them is committed instead: the prompt set, the oracle's lockfile and the pinned model commit. The f32 fixtures generated on a different machine may differ from another machine's in the rounding of the f32 reference itself, and against which the engine's error in release 0.1.1 reached 99% of S-1; that is why S-1 is judged against the f64 fixtures, whose machine-to-machine differences are expected to be orders of magnitude smaller (measured, plan 0.1.2). The manifest records which machine produced them.

## 11. Correctness harness

Rust integration tests in `tests/`, run with `cargo test`; the test profile is compiled with optimization and debug assertions on, so a full run takes seconds instead of minutes without losing overflow checks (FR-7).

- The harness reads every `fixtures/*/manifest.json`, so a new model's fixtures are picked up without code changes.
- Per prompt it checks encoding (FR-13), decoding (FR-14), logits (S-1), intermediates (S-2), top-1 token (S-3) and greedy continuation (S-4). The logits, intermediates and top-1 come from `prefill` with `Logits::All` and capture on, in one pass over the prompt (FR-41); the greedy continuation is generation as the engine runs it, a batched prefill and then decode steps from the cache it filled, so S-4 judges the two paths together. Judging the batched pass instead of feeding the tokens one at a time changes how the engine's values are obtained, not what they are compared with: the thresholds, the f64 reference and the near-tie rule are untouched. The numeric checks and the near-tie rule read the f64 fixtures (§10). The engine's f32 values are widened to f64 before the difference is taken, so the comparison adds no rounding of its own and the f64 reference is never narrowed.
- Beside each logit and intermediate error it also measures the engine's distance to the f32 fixtures and reports it, per category, in the same table. This figure never fails a prompt (FR-5). The token encoding, decoding and streaming checks read the manifest's existing fields, which are the 32-bit run's: they test the tokenizer, whose result does not depend on the arithmetic, and the two runs' continuations were identical on every prompt when measured (plan 0.1.2 §4).
- For `utf8-split` prompts it streams the expected continuation through the streaming decoder and checks that the concatenated chunks equal the full decode and that no chunk contains a replacement character the full decode lacks (FR-15).
- A tensor, for S-2, is one layer's `[positions, hidden]` output for one prompt, and its largest magnitude is taken over all positions; a per-position maximum would be stricter. An all-zero reference tensor fails. A near-tie is an f64 reference gap strictly less than 1e-3, and in the greedy comparison the gap before each continuation token decides: the first near-tie stops the comparison, tokens before it must match, and the token at it may be either (S-3, S-4).
- **Batched against one-token (FR-41).** A separate test, outside the S-judged tables, runs the same prompts through both paths and reports the largest logit and intermediate difference between them. Until release 0.4.1 it failed above 1e-5 absolute in logits and the difference was exactly 0 on every prompt (releases 0.4.0 and 0.4.1), because the two paths did the same arithmetic in a different loop order. From 0.4.2 the batched products sum in fused chunks and the one-token products in 16 partial sums (§4), so the difference is no longer 0: the worst over the prompt set is 3.53e-4 in logits, and the bound is 1e-3 (S-1's tolerance, 2.8 times the worst; initial; tune with use), because two computations each within S-1 of the reference may differ by that much and a defect in either is far larger. The test keeps its job of catching a defect in one path.
- **Blocked against unblocked (FR-47).** A separate test, outside the S-judged tables, runs the prompt set through `prefill` with the blocked product and with the retained 0.4.1 `matmul`, and reports the largest logit and intermediate difference; it fails above the same bound, 1e-3 (worst measured 3.53e-4, the same prompt). The two compute the same products with different orders of addition, so a difference far above rounding is a defect in the blocked kernel that S-1's tolerance against the reference could absorb. Run with a faulted blocked product (`UnfinishedTile`, §17) the difference is far over the bound.
- **Thread-count independence (FR-43).** A separate test, outside the S-judged tables, runs the same prompts at thread counts 1, 2, 3, 7 and the default, and fails on any difference in any logit or captured intermediate: the bound is exactly 0, because the work is divided without changing any sum. The S-judged tables run at the default count, which is what generation uses; with the identity checked, judging at one count judges all.
- **Sampling checks (S-9, S-10).** Per prompt and setting, the harness computes the engine's adjusted distribution from the engine's own logits at the last prompt position (§8) and reports the largest absolute probability difference from the stored distribution, judged by the tolerance of Requirements S-9 (1e-5). Every setting is judged; the smallest margin to each cutoff is reported beside the errors so a cutoff the engine's rounding could cross would be visible. The draw test (S-10) is a unit-level test: for a fixed logit vector, a fixed seed and 200,000 draws, token counts are compared with the distribution by a chi-square statistic over tokens pooled until each expects at least 5 draws, and the test passes when the statistic is at most df + 4·sqrt(2·df), a normal approximation with a tail of about 3e-5 (initial; tune with use). The seed is fixed, so the result is the same on every run.
- **Chat checks (S-11, FR-39).** Per conversation in `chat.json` the harness renders the stored messages with `render` (§8) and compares the text with the stored text character for character, then encodes the engine's rendering and compares the ids with the stored ids; both are judged and reported by name, a text mismatch with the first differing character and a token mismatch with the first differing position, because a text that matches can still encode wrongly (FR-33). The check takes the renderer and the encoder as arguments, so the negative controls can substitute faulty ones (§17). Beside them, per conversation, the harness feeds the stored token IDs through the forward pass and reports the largest logit difference from the f64 logits, and generates the greedy reply and reports whether its IDs equal the stored reply's up to the first near-tie (the rule of S-3 and S-4). Those two figures fill a table labelled *reported only (instruct)* and never fail a conversation or a release (Requirements §13, FR-5). A missing instruct model directory or `chat.json` fails the run naming the path or the oracle command, as for the base model.
- It prints a pass/fail table by prompt and by category; any failing category fails the run (S-5). Each failure reports the first diverging position and, for intermediates, the first diverging layer (FR-6).
- Model files are found in `models/<model-id>/` (git-ignored, filled by the oracle's download script). If they are missing, the run fails naming the path; it never downloads (FR-7). Missing fixtures, f32 or f64, fail the run the same way, naming the oracle command that generates them.

## 12. Benchmark harness

A custom harness in `benches/`, run with `cargo bench`, which builds with the optimized profile. It also refuses to run if debug assertions are enabled, as a second guard (FR-10).

- **Workloads.** A short prompt of 32 tokens and a long prompt of 512 tokens, each followed by 128 generated tokens. Initial values; changing them starts a new comparable series in the record.
- **Metrics (FR-8).**
  - Prompt throughput: prompt tokens divided by prompt time.
  - Generation throughput: generated tokens divided by generation time.
  - Time to first token: from receiving the prompt string to the first generated token.
  - Peak resident memory.

  Model load time is reported separately, so it does not distort time to first token.
- **Isolation.** Each workload runs in a fresh child process, because peak resident memory is a per-process high-water mark and would otherwise carry over.
- **Repetition.** Each workload runs 5 times; median, minimum and maximum are recorded (S-7).
- **Record (FR-9).** One JSON line per workload is appended to `results/benchmarks.jsonl`: package version, commit and whether the tree was dirty, CPU model, core count, memory, OS, build profile, timestamp, and results.
- **Kernel baseline (HC-2).** A separate group times the in-house matrix-vector product against the test-only linear algebra crate (`matrixmultiply`, single-threaded) at the model's five matrix shapes. It agrees with both before timing and records one row per shape with ns per call and GFLOP/s. The group is reached through the `bench-kernels` Cargo feature, off by default, which adds the public module `emberly_oxygen::kernels`; only the library's self-referencing dev-dependency enables it, so a normal build never contains it.
- **Reference points for the kernel.** `matrixmultiply` is a weak yardstick for a matrix-vector product: built for matrix-matrix work, it is only about 1.25× faster than the 0.1.0 loop at most shapes and slower at the 49152×576 output projection, because it repacks the matrix on every call. The kernel group therefore also times the 0.1.0 index-order loop and the partial-sum widths swept, 4, 8, 16 and 32 (FR-25), so the speed-up is shown against the engine's own history. A dedicated matrix-vector library is not added as a baseline in release 0.1.1: it would be a new dependency (§15) and the earlier loop already shows the ceiling.
- **Batched kernel rows (FR-48).** In the kernel group, at the three shapes of the batched products (1536 × 576, 576 × 1536, 576 × 576) with 128 input rows, single-threaded, in this process: the 0.4.1 `matmul`, `matmul_blocked` and `matrixmultiply`'s sgemm (HC-2), as GFLOP/s, one line per shape and kernel with `"inputs": 128` and `"threads": 1`. The blocked kernel is checked against the chunked fused sum before it is timed, so a number is never recorded for a kernel that computes something else. The prefill and thread sweeps run as before, so 0.4.2's rows are read against 0.4.1's at the same lengths and counts, and the decode rows show whether decode moved.
- **Comparability.** The workloads and procedure are unchanged from 0.1.0, so every release's rows are compared with the previous release's in the record, and 0.1.0's are the baseline (FR-9, FR-25).
- **Prefill sweep (FR-42).** A group in the same harness, reached like the kernel group (it also runs alone with `--prefill-only`), times the prompt alone, from the first token of the prompt to the logits of its last position, at 32, 67, 128, 512 and 644 prompt tokens. 67 and 644 are the lengths of the first and last turn of the ten-turn chat in the 0.3.0 note (§2), so chat time to first token is the sweep's rows at those lengths and no chat benchmark is added. The prompts are the first `n` token IDs of the longest workload's prompt (512 tokens), repeated from its start for lengths beyond it, so every run feeds the same tokens; the time depends on the length and not on the text. Each length is run on two paths in the same build, in one process after a warm-up run: **one-token** (the 0.3.0 way: one `step` per token) and **batched** (`prefill`, `Logits::Last`). The release is compared with the previous one directly: the figures include everything the change did, and no intermediate path is built to apportion them. The paths are checked to agree on the last logits within the bound of §11 before any timing, and nothing is recorded if they do not. Repetition and statistics are those of S-7 (5 runs, median, minimum, maximum). One JSON line per (length, path) is appended to the record with `"group": "prefill"`, `"path"` (`one_token` or `batched`), `"prompt_tokens"`, the metric `prompt_ms` and the same conditions (FR-9). The one-token path exists as a measurement only here; the two workloads time the engine as released.
- **Workloads and the sweep.** The 32 and 512 token workloads of this section run the released engine, so from 0.4.0 their prompt time is batched. Their rows stay comparable with earlier releases' only in what the engine does, not in how it does it, which is the point of the release; the previous release's rows are the baseline FR-42 and the note compare against.
- **Thread count in the record (FR-44, FR-9).** Every row carries `threads`, the count in use. Rows recorded before 0.4.1 have no such field and were single-threaded. The two workloads run at the default count.
- **Thread sweep (FR-45).** A group in the same harness, with `"group": "threads"`, runs the released engine at 1, 2, 4, 8, 12 and 16 threads (initial; counts above the machine's available cores are left out) and times, in one process after a warm-up run, the prompt alone at 128 and 644 tokens (the `batched` path of the prefill sweep) and the generation of 128 tokens after a prompt of 32 tokens and after one of 512 tokens, as milliseconds per generated token. One JSON line per (count, phase, length) is appended with `"threads"`, `"phase"` (`prompt` or `decode`), `"context_tokens"` and the metric, and the same conditions as every row. The thread counts are checked to give identical last logits before any timing, and nothing is recorded if they do not (FR-43). The release is compared with 0.4.0's rows directly (its prefill sweep and workloads are single-threaded, so 0.4.0's rows at the same lengths are the baseline); no intermediate engine is built, so the figures include threaded products and threaded attention together, and the release note apportions them only by their shares of a step from the profile (FR-45). The one-thread row of the same build shows what the pool's presence alone costs. The sweep picks the default thread count: the count with the highest decode speed at 512 tokens, counts within 2% of the best decode time being ties and a tie going to the count with the faster prompt at 644 tokens (initial; tune with use). The tie goes to the faster prompt and not to the smaller count (owner, 2026-11-11) because decode stops gaining beyond a few threads while the prompt keeps gaining to the performance cores, so a smaller-count tie rule would give up most of the prompt's speed for under 1% of decode.
- **Sampling cost.** A kernel-style group times one sampling step on a 49152-logit vector with every control neutral (the baseline of the draw and the softmax), for each control alone and for all four, so the release note can state what a sampled step costs next to a forward step. It is a measurement of the new code only: the two workloads run greedy, as in every earlier release, so their rows stay comparable (FR-9, FR-29).
- **Chat cost.** There is no new benchmark group: rendering is string work, and a turn's cost is processing the whole history through the forward pass (§2), which the 512-token workload already measures per token. The release re-runs the two greedy workloads for its rows, as every release does (§16), so the record keeps one comparable series. That chat left the greedy path alone is shown by a test that pins the ids of greedy and seeded runs (FR-29), not by the rows, which move with the session by a few percent (S-7).
- **Definitions.** Throughput and time to first token are as defined in §8.

## 13. Configuration

There is no configuration file. Run settings, sampling and chat included, come from command-line flags (§9) and model settings from the model's own `config.json` (§3); nothing else is configurable, because nothing else is required.

## 14. Error handling and logging

- The library returns one error type with a variant per failure class: I/O, malformed file, unsupported model or tokenizer component (naming the field and value, FR-12), tensor mismatch (naming the tensor), and request rejected (empty prompt, context exceeded, FR-18, a conversation that no longer fits, FR-36, or an invalid sampling value, FR-30). A rejected chat turn is not fatal: the chat command prints it and continues (§9).
- User input never causes a panic. Panics are reserved for broken internal invariants, which are bugs.
- The binary prints the error to standard error and exits with code 1; command-line usage errors exit with code 2 (FR-20). Text already streamed before a mid-generation error stays printed; the error follows on standard error.

**Logging.** The library emits events through the `tracing` crate and never prints (FR-22); the CLI installs the subscriber that formats and routes them. Verbosity is set by repeating `-v` (FR-23):

| Flag | Level | Content |
| --- | --- | --- |
| none | warn | warnings and errors |
| `-v` | info | model and configuration summary, thread count, load time, prompt token count, run summary with throughput |
| `-vv` | debug | one event per forward step: position, the token fed, its text, top 5 candidates with logits, step time; a step whose result is taken also names the chosen token as `next` and, when sampling, its probability and the number of tokens left after the filters (computed only at this level, S-8); the prompt gives one `prefill` event instead of one per token (positions, time, whether all logits were computed), and the first token's `next` is reported on it. Since the last generated token is never fed (§8), a run has one prefill event plus generated tokens minus one step events |
| `-vvv` | trace | per layer within each step (within the prefill, per layer once for the whole prompt, with the statistics of the last row): residual-stream norm after attention and after the MLP, and for each head the position receiving the most attention weight |

- Generation, prefill, steps and layers are nested spans (`generate` → `prefill` or `step{pos}` → `layer{idx}`), so every event carries its place in the decode loop.
- `--log-file <path>` sends the same events to a file instead of standard error (FR-24). Standard output stays generated text only (FR-20).
- Per-layer statistics are computed only when the trace level is enabled, so lower levels do no extra arithmetic. No statistic feeds back into the computation, so output is identical at every level (S-8). The benchmark harness runs at the default level.
- Logging costs nothing measurable when no subscriber is installed: the real model's step time was 49.25 ms before logging was added and 49.29 to 49.32 ms after.
- At trace level a 512-token prompt now produces one event per layer rather than tens of thousands, but the decode steps that follow do not change. It is meant for short prompts, or with `--log-file`.

## 16. Build and release

- Stable Rust, edition 2024. Release builds use Cargo's default optimized profile; the test profile is raised to full optimization with debug assertions kept (§11).
- Versions follow semantic versioning: before 1.0, a release introducing a new capability bumps the minor version and a fix bumps the patch version (Requirements §12). The optimisation series after 0.4.0 is the exception, by the owner's decision of 2026-11-11: each kernel technique is a patch release (0.4.1 threads, then 0.4.2, and so on), so the series reads as one line.
- Release steps, in order:
  1. `cargo test` passes (HC-4).
  2. `cargo bench` runs on the benchmark machine and appends to the record.
  3. The release note is written to `docs/releases/<version>.md`.
  4. The commit is tagged `v<version>`.

  Benchmarks follow the correctness run, so no result from a failing build enters the record (HC-4). Running straight after the tests leaves the machine warm: in 0.1.0 it made the workloads about 6% slower than on an idle machine. The procedure is kept as written so that every release's rows are taken the same way and stay comparable (S-7); the effect is a known bias, not a correction.

## 17. Testing strategy

- **Unit tests per kernel.** Each kernel is checked against hand-computed small cases (softmax sums to 1, RoPE at position 0 is the identity) and, for matrix-vector product, against the test-only linear algebra crate on random inputs (HC-2).
- **Unit tests for the tokenizer.** Byte-map round trips, merge order on known pieces, and the streaming decoder's hold-back on split three-byte characters (FR-15).
- **Correctness harness.** End-to-end comparison against the oracle's fixtures (§11), the gate every release must pass (HC-4).
- **Negative controls.** The harness must be seen to fail. A Cargo feature, `negative-controls`, off by default, adds the enum `Fault` (`InterleavedRope`, `PerturbedLogit { position }`, `NoFinalNorm`, for the batched pass `UnmaskedAttention`, for the threaded products `SkippedRows`, and for the blocked product `UnfinishedTile`) and `Model::inject_fault`; in a normal build `Fault` has no values, so no faulty arithmetic is compiled in. The library's self-referencing dev-dependency enables the feature, so plain `cargo test` always runs the controls and none is skipped for a missing flag, while `cargo build` never contains them. `SkippedRows` leaves the last worker's rows of every threaded product unwritten, as a partition that dropped a range would; S-1 must fail on it, and the control runs with an explicit count of 4 workers so it does not depend on the machine's default (FR-43). `UnfinishedTile` leaves the last, partial tile of every blocked product (the leftover rows or inputs that do not fill a tile) unwritten, as a loop that forgot its edge would; S-1 must fail on it, and the prompt set contains lengths that are not a multiple of the tile's input width so the edge is exercised (FR-46). `UnmaskedAttention` makes every row of `prefill` attend to the whole prompt, as a missing causal mask would (FR-40); S-1 must fail on it, so the check that the batched pass respects the future is seen to be able to fail. The existing three faults are injected in `prefill` too, and the harness, which now reaches the engine through it (§11), must fail on each as before. A test asserts that the harness fails on each fault. With no fault injected the feature changes no result. A check that has never failed has not been shown to work. The new kernel (§4) must leave all three controls failing as before, and so must the move to the f64 reference: the controls are run against it, and the `PerturbedLogit` size is checked to exceed the S-1 limit in force, so that a change of limit cannot leave a control that no longer fails.
- **Batched pass tests.** On the tiny model of the forward tests: `prefill` with `Logits::All` equals the one-token logits and capture at every position within 1e-5 (FR-40, FR-41); a token changed after position `t` leaves the logits at positions up to `t` bit-for-bit equal, which is the test that the mask is causal; the cache holds the same keys and values as the one-token path; a one-token prompt and a prompt that fills the context exactly both work, a prompt one token too long is rejected before any computation and leaves the cache empty (FR-18); `Logits::Last` equals the last row of `Logits::All` within 1e-5 (the last position's unembedding is a matrix-vector product and the all-position one a blocked product, so from 0.4.2 not bit for bit); and the first generated token and a short greedy run are the same ids whether the prompt went through `prefill` or through `step` on the tiny model. The matrix-matrix product is checked against `matvec` row by row, which must be equal, and against `matrixmultiply`, at the model's shapes and at lengths and row counts that are not a multiple of anything (HC-2, FR-40).
- **Blocked kernel tests (FR-46, FR-47).** `matmul_blocked` equals the chunked fused sum written out plainly in the test, element by element, exactly: at the model's shapes; at row counts and input counts that do not divide the tile, are smaller than the tile, or are 1; at lengths below and above the vector width; and at thread counts 1, 2, 3, 7 and 16, so neither the tile nor the row division changes a bit. It is shown equal to `matrixmultiply` within a tolerance far below S-1 (HC-2), and a test that sums with 16 partial sums instead must differ in some bit, so a comparison that cannot see a changed order of additions would be caught. A tile edge test marks every output element of a product with a known value and checks that none is left unwritten.
- **Threaded kernel tests (FR-43).** `matvec`, `matmul` and the attention at thread counts 1, 2, 3, 4, 7 and 16 produce results equal bit for bit to the single-threaded call, at the model's shapes and at row counts that are not a multiple of the thread count, with fewer rows than threads and with one row; a `step` and a `prefill` on the tiny model equal their single-threaded logits, cache and capture bit for bit at each count. The equality check is shown able to fail by the negative control `SkippedRows` and by a deliberate perturbation of the threaded product, which the kernel test and the real-model test must both fail on (plan 0.4.1 §5). Pool tests: many calls in a row reuse the workers; loading and dropping a model repeatedly neither hangs nor leaves threads running; a count of 0 is rejected naming `threads` (FR-44).
- **Kernel tests.** The new matrix-vector product is checked against the 0.1.0 index-order loop and against `matrixmultiply` on random inputs at the model's shapes and at lengths that are not a multiple of 8, including lengths below 8 (the tail), within an absolute tolerance far below S-1 (HC-2, FR-25).
- **Reference tests.** The comparison functions are given a reference value that f32 cannot represent and must measure the error against the unrounded value (S-1, FR-2); the f64 fixtures are checked to have the manifest's shapes and dtype (FR-4); the oracle's own start-up check that the 64-bit RMSNorm and softmax are active (§10) is run whenever the oracle is; and a test shows that the f32 distance never turns a passing prompt into a failing one (FR-5).
- **Sampling tests.** Each control against hand-computed small distributions (FR-26, FR-27): the penalty's sign rule, top-k with a tie at the cutoff, top-p at its boundary and with p small enough to keep one token. The generator against published xoshiro256** outputs for a known seed. Seeded reproduction: the same seed gives the same tokens, a different seed gives different tokens (FR-28). Validation rejects each invalid value, naming the option (FR-30). Greedy is unchanged: the whole existing harness runs untouched, and temperature 0 with every other control set produces the same IDs as the default (FR-29). The chi-square test of §11 (S-10) is shown able to fail by feeding it draws from a different distribution.
- **Sampling negative controls.** `Fault` gains `SwappedSamplingOrder` (top-p applied before temperature) and `PenaltyWrongSign` (the penalty is inverted: positive logits are multiplied and negative ones divided); S-9 must fail on each, so the distribution check is seen to fail. The swap is top-p and temperature because temperature divides by a positive number, which keeps the ranking, so it commutes with top-k and swapping those two changes nothing S-9 could see. The controls run on a prompt where both faults are far over the tolerance (`thai-medium`: 0.05 and 0.85), not one where a fault is weak (the inverted penalty moves `english-short` by only 7.7e-3), and on a combined setting that keeps several tokens. With no fault every setting passes.
- **Chat tests.** `render` against hand-written strings: no system message (the default one is added), a system message first, a system message not first (rendered as given), several turns, empty content, and the generation prompt present and absent (FR-33). The markers encode as IDs 1 and 2 with the instruct tokenizer (FR-33, §6). On the real instruct model with greedy settings: a reply ends at `<|im_end|>` and the end token is not streamed (FR-34); a turn appends exactly a user and an assistant message and the assistant's content equals the text streamed (FR-35); a reply cut by a tiny maximum is closed by the next prompt's rendering (FR-34); the second turn's prompt contains both earlier messages (FR-35); a turn whose maximum new tokens cannot fit is rejected before any computation and leaves the messages as they were, and a later turn works (FR-36); the same seed and messages replay the same replies and another seed does not (FR-37, FR-28); temperature 0 gives the same ids as `generate` on the rendered text (FR-29). The CLI package runs the built binary with piped input: standard output holds only replies (FR-38, FR-20), the marker and the seed line go to standard error and the seed line appears once, `/exit` and end of input end the chat with code 0, a blank line sends nothing, a rejected turn prints its error and the chat continues, and `--temperature 0` alone produces no warning.
- **Chat negative controls.** S-11's check is shown to fail by giving it faulty renderers and encoders, kept in the tests (the template is not model arithmetic, so no `Fault` is added and no faulty code is compiled into the library): a renderer with no default system message, a renderer without the newline after `<|im_end|>`, and an encoder that spells the markers out as characters, which must fail on tokens while the text still matches. With the real functions every conversation passes.
- Every test names the HC, FR or S item it verifies, so coverage of the Requirements can be listed mechanically.

## 19. Open Items

### Resolved since 0.4

- **The tile shape and the bounds of the blocked-against-unblocked and batched-against-one-token tests (§4, §11, FR-47).** The tile is 4 × 16 with chunks of 64: the fastest of eight shapes at all three prompt shapes in the real code (93.5 to 110.9 GFLOP/s against the 0.4.1 loop's 36 to 38 and sgemm's 106), and the chunks bring the error against the reference below 0.4.1's. - **How the workers read the weights and the key-value cache in safe code (§4, FR-43).** Persistent workers; the weights shared as `Arc` (a tensor's data is shared, so a clone copies the shape and not the numbers); the small input copied per call; each worker's output returned over a channel; each layer's cache vectors shared as `Arc`, the workers dropping their handles before they answer so the next append extends the vector in place. Scoped threads per call were rejected on cost (§4). No `unsafe`. Decided by the owner on 2026-11-11 after the measurements of plan 0.4.1 §5.
