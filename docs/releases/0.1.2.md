# Emberly Oxygen 0.1.2 — Release note

Nov 8, 2026 · @Wattanit

**One change: the correctness gate judges the engine against a float64 reference, not against PyTorch's float32 output.** The engine does not change; 0.1.2's code is 0.1.1's. The release exists because [0.1.1](0.1.1.md) found that S-1 measured distance to PyTorch's rounding, not to the correct answer: a correct engine reached 99% of S-1's limit. Against the float64 reference the same engine's worst logit error is 35% of S-1 and its worst intermediate error 10% of S-2, with the thresholds unchanged. Built against Requirements 0.4 (approved) and Technical Specification 0.3 (its status is still `draft`; the owner sets it). The detailed record is the [implementation plan](../emberly-oxygen-implementation-plan-0.1.2.md) (§4 measurements, §5 feedback) and the per-phase to-dos in [`docs/todo/`](../todo/).

## What changed

- **The oracle runs the model twice, in float64 and in float32, from the same weights.** The float64 run is the reference. The float32 run is what the library computes by default; it is kept so the harness can report the engine's distance to it. Per prompt there are now two safetensors files (`<id>.safetensors`, `<id>.f64.safetensors`) and the manifest gains `f64_` fields. Both runs take about 98 s and the fixtures folder grew from about 0.7 GB to 2.0 GB.
- **In the float64 run, RMSNorm and the attention softmax are forced to float64.** The pinned transformers computes both in float32 even inside a float64 model (see below). A context manager replaces them for that run only and restores the library afterwards, so the float32 run is the plain library; a start-up check, shown to fail without the replacement, confirms it is active. The rotary tables are left as the library makes them (float32): they are the model as published.
- **S-1 to S-4 are judged against the float64 reference** (FR-2, Requirements 0.4): logits, intermediates, top token, and the greedy continuation with its near-tie rule. The engine's float32 values are widened exactly before each difference is taken, so the comparison adds no rounding and the reference is never narrowed.
- **The distance to the float32 reference is reported and judges nothing** (FR-5): the category table has a labelled "reported only" pair of columns, kept in a separate field of the result that no verdict reads.
- **The thresholds are unchanged** (S-1 1e-3, S-2 1e-4, near-tie gap 1e-3), by the owner's decision against a rule agreed before the numbers were seen: keep a limit when the worst error is at most half of it.
- **The negative controls fail against the new reference,** and a new test measures the logit perturbation (1.9999e-3) by running with and without the fault, so loosening S-1 to it or past it fails loudly. The engine's source is untouched; only the version number changed.
- **The test suite gained 16 tests** (reader, manifest, comparison, report, controls): **230 tests** now run in 24 to 29 s.
- **Requirements 0.4 corrects 0.3** (FR-2, see below) and absorbs the FR-25 figure (94% of a 0.1.0 step, not 98.6%); the Specification's §10 and §17 follow.

## Why it was expected to help

0.1.1 found that any partial-sum order moved the engine 1.4× to 8× further from PyTorch's float32 output, while a one-off float64 diagnostic showed the engine had not become less accurate: PyTorch's own float32 run was up to 7.1e-4 from the true value. A check whose limit the reference's own rounding can nearly exhaust cannot tell a correct engine from a broken one. Judging against the float64 result puts the yardstick where the correct answer is.

## What was measured

Apple M4 Max, commit `e132ab0` for the benchmark (clean tree, version 0.1.2, straight after `cargo test` passed, 230 tests).

**The engine against the float64 reference** (worst logit error against S-1's 1e-3, worst relative intermediate error against S-2's 1e-4; share of the limit in brackets), with the distance to the float32 reference beside them:

| Category | Logit vs f64 | Intermediate vs f64 | Logit vs f32 | Intermediate vs f32 |
| --- | --- | --- | --- | --- |
| english | 2.45e-4 (25%) | 6.13e-6 (6%) | 3.14e-4 | 3.66e-5 |
| thai | 1.22e-4 (12%) | 9.97e-6 (10%) | 2.79e-4 | 1.51e-5 |
| code | 1.23e-4 (12%) | 5.24e-6 (5%) | 3.18e-4 | 4.02e-5 |
| utf8-split | **3.50e-4 (35%)** | 7.80e-6 (8%) | 9.90e-4 | 2.70e-5 |
| long | 2.45e-4 (25%) | 5.25e-6 (5%) | 3.18e-4 | 2.99e-5 |

The "vs f32" columns reproduce 0.1.1's table digit for digit, so the same engine that sat at 99% of S-1 against the float32 reference sits at 35% against the float64 one. Every prompt passes every check; no greedy continuation differs between the two references.

**Three kernels against the float64 reference** (a scratchpad run, not in the repository: the kernel's width changed to 1 and to 8, run, restored). Worst logit error and worst relative intermediate error:

| | 1 sum (0.1.0's order) | 8 sums | 16 sums (released) |
| --- | --- | --- | --- |
| Logit | 4.58e-4 | 3.20e-4 | 3.50e-4 |
| Intermediate | 4.37e-5 (44% of S-2) | 1.32e-5 | 9.97e-6 |

**The reference's own noise** (the f64 pass rerun at another thread count against the stored files; worst logit difference): the plain library's float64 run gave up to 1.74e-5 at one thread (exact at the 12 threads that generated it); the released reference, with RMSNorm and softmax in float64, gives 2.18e-6. The float32 and float64 fixtures differ by up to 6.39e-4 in logits (`utf8-split-cjk`; 7.13e-4 against the plain library run).

**Speed is unchanged, and this release does not claim otherwise.** The benchmark re-ran because the version changed. The short workload and the kernel reproduce 0.1.1's rows to 0.3% and 0.1%: generation 117.8 tokens/s (0.1.1: 117.5), the kernel 35.4 to 38.7 GFLOP/s (0.1.1: 35.4 to 38.3), peak memory 811.6 MB, model load 60.5 ms. The long workload was 5% faster than 0.1.1's rows (generation 83.8 tokens/s against 79.8, first token 4.93 s against 5.18 s) with identical code; see below. The whole bench took 3 minutes 51 seconds.

## What was learned

- **The library's "float64" model is not float64.** In the pinned transformers (5.21.0) RMSNorm casts to float32, the attention softmax is requested in float32, and the rotary tables are computed in float32, even when the model's dtype is float64. The first float64 run therefore contained float32 rounding that depended on the thread count (up to 1.74e-5 in logits, over the 1e-5 bar set for this task), and the version with those two operations in float64 differed from it by up to 7.3e-5. **My Requirements 0.3 and Specification draft said the reference was "exact in arithmetic"; that was wrong,** found by the noise check and corrected in Requirements 0.4 and Specification §10. The rotary tables are still float32, so the reference is the library's definition of the model in 64-bit arithmetic, not an independent implementation.
- **Against the truth, the partial sums are better than 0.1.0's order, not worse.** The worst intermediate error falls 4.4× (4.37e-5 to 9.97e-6) and the worst logit error from 4.58e-4 to 3.50e-4. The 8-sum kernel is slightly better than 16 on the worst logit (3.20e-4 against 3.50e-4); the difference is small, and the width was chosen for speed.
- **The margin was a property of the yardstick.** S-1 was at 99% against a float32 reference whose own error was up to 7.1e-4; against the float64 reference it is at 35%, and S-2 is at 10%. That is why the thresholds were kept: the numbers, not a decision to loosen, closed the gap.
- **One benchmark session on this machine can differ from another by 5% on the long workload.** 0.1.1's long-workload range was already wide (a 4% spread); 0.1.2's is tight (0.3%) and sits above it. 0.1.1's 4.3× long-generation gain over 0.1.0 could equally be stated as 4.5×. The short workload and the kernel are far steadier.

## Negative results

- **The plain library float64 run failed its own noise bar** (1.74e-5 against 1e-5) and was not used. The owner chose the corrected reference over keeping the plain run with a relaxed bar.
- **A cause for the remaining 2e-6 was not found.** The reference's thread-count difference is 2.18e-6 on the thai and long prompts only, and zero or about 1e-13 elsewhere. The float32 rotary tables are one candidate; nothing was done to find out.
- **Not measured: another machine.** The reference's noise was measured across thread counts on one machine only; whether fixtures regenerated elsewhere differ by more is untested, which is the original trigger for this work.
- **No explanation for the 5% long-workload difference** between two measurements of identical code. Candidates (the machine's state, code placement after the rebuild, chance) were neither investigated nor ruled out.

## What comes next

The next Requirements bump moves the thresholds question to its resolved ledger with these figures and corrects nothing else in this release's scope. The roadmap's next version is v2, sampling and chat; the engine is fast enough (about 118 tokens/s on short prompts) and the gate now measures correctness against the right target. If speed is wanted first, the 0.1.1 note's suggestion stands: profile attention and the other operations before more kernel work, since on long prompts about 42% of a step is outside the matrix-vector product.
