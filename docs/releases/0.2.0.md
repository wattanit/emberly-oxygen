# Emberly Oxygen 0.2.0 — Release note

Nov 8, 2026 · @Wattanit

**One feature: sampled generation.** The engine can now choose the next token by sampling, with temperature, top-k, top-p and a repetition penalty, drawn from a seeded random number generator written in this project. Greedy generation is unchanged, and so is its speed: the greedy benchmark workloads reproduce 0.1.2's rows to within 1.6%, the long workload's generation figure to the third decimal. The release also changes how correctness is judged, because a sampled run has no single right output: sampling is checked by the distribution it draws from and by statistics over its draws, not by matching a reference's tokens. Built against Requirements 0.6 and Technical Specification 0.4, both approved by the owner on 2026-11-08, edited in place with the owner's permission with what the work found (the tolerance of S-9, the corrected negative control, the signature of `generate_with`) and approved again the same day after a compliance review. The detailed record is the [implementation plan](../emberly-oxygen-implementation-plan-0.2.0.md) (§5 measurements, §6 feedback) and the per-phase to-dos in [`docs/todo/`](../todo/).

## What changed

- **Four controls, in the reference library's order** (FR-26, FR-27): repetition penalty, then temperature, then top-k, then top-p, then one draw. The penalty divides a positive score and multiplies a negative one for each distinct token already in the prompt or the output, as the library does. Top-k keeps the k highest tokens and every token tied with the k-th, as the library does. Top-p uses the library's rule (sorted ascending, remove while the running sum is at most 1 − p, always keep the highest token). The controls run in f32; the softmax and the draw run in f64. A temperature of 0 is greedy selection and ignores the other controls, with a warning.
- **Seeded generation, reproducible within a build** (FR-28): xoshiro256** seeded through SplitMix64, written in this project, one draw per chosen token. The same build, model, prompt, settings and seed give the same tokens. The seed is not promised across releases: pinning the generator forever would bind every later release to one algorithm.
- **The command-line tool** (FR-30): `--temperature`, `--top-k`, `--top-p`, `--repetition-penalty` and `--seed`, all neutral by default, so a run without them is the greedy run with an empty standard error. When sampling, the tool prints `seed: <n>` to standard error before any text, taking the seed from the clock if none was given, so any run can be replayed. An invalid value is an error naming the option and the value.
- **The oracle stores the expected adjusted distributions** (FR-31): `oracle/sampling_reference.py` reads the stored float64 logits (it does not run the model again, so it takes 1 s) and writes, for twelve prompts and five settings (each control alone and all four), the distribution the library's own processors give, 60 in all and 23 MB, with the margin to each cutoff in the manifest.
- **Two new checks** (S-9, S-10). S-9: the engine's adjusted distribution at each prompt's last position matches the stored one within **1e-5**. S-10: over 200,000 draws with a fixed seed, a chi-square statistic stays within its limit. The existing S-1 to S-8 are untouched and pass as before.
- **Negative controls for sampling.** Two deliberate faults, a swapped order (top-p before temperature) and an inverted penalty, make S-9 fail by 0.05 and by 0.85 to 0.97, and nothing else fails with them.
- **The debug log** shows, for a sampled step, the chosen token's probability and how many tokens the controls left. **The benchmark** gains a sampling-cost group; the two workloads stay greedy.
- **The test suite grew by 74 tests**: **304 tests** now run in about 25 s.

## Why it was expected to help

The roadmap's v2 is usable, non-deterministic generation. Greedy output repeats and cannot be varied; sampling is the minimum the engine needs before chat. The owner's reasoning for the checks: the oracle's tight token-by-token matching served the stage of proving the engine equal to the library, and a sampled run has nothing to match, so the new features are judged on what has a correct answer: the distribution before the draw, and the statistics after it.

## What was measured

Apple M4 Max, commit `7e69bb4` for the benchmark (clean tree, version 0.2.0, straight after `cargo test` passed, 304 tests).

**S-9, the engine's distribution against the stored one** (largest absolute probability difference, 60 distributions): worst **1.98e-6** (temperature 0.7 on `utf8-split-emoji`); per category and setting between 3.2e-7 and 2.0e-6. The tolerance, 1e-5, is the smallest round decimal at least twice the worst error, the rule used for S-1. A numpy recomputation written from the textbook definitions, with no library code, agrees with the library's distributions to 1.1e-13, and no top-k tie occurred. No cutoff was crossed on any prompt: the engine's logit error at the last prompt position is at most 5.05e-5, the smallest top-k margin is 2.18e-4 (4.3 times that) and the smallest top-p margin is 6.79e-5 in probability (49 times the matching probability error).

**S-10, draws against the distribution** (200,000 draws, fixed seed, tokens pooled to at least 5 expected): 9.0 over 12 degrees of freedom (limit 31.6) with no controls, and 442.7 over 422 (limit 538.2) with temperature 0.7, top-k 40 and top-p 0.9. The test fails on draws from another temperature, on draws that skip top-p, on another top-k, and on a sampler biased by 2%.

**The greedy path is unchanged** (medians, 0.1.2 → 0.2.0): short workload generation 117.82 → 117.89 tokens/s (+0.06%), first token 256.8 → 256.5 ms; long workload generation 83.810 → 83.809 tokens/s, first token 4927.2 → 4927.0 ms; peak memory 811.6 MB both; model load 60.5 → 61.4 ms; the kernel's five shapes 35.4 to 38.7 → 35.4 to 38.4 GFLOP/s (−0.8% to +1.0%). The whole bench took 302 s.

**What a sampled step costs** (one step on 49152 logits, median, five runs): no filtering **162 us**, temperature 0.7 165 us, top-k 40 182 us, penalty 1.3 163 us, top-p 0.9 **934 us**, all four 562 us. A forward step is 8.5 ms on the short workload and 11.9 ms on the long one, so a sampled step adds 1.9% to 11% of a short-workload step.

## What was learned

- **Temperature and top-k commute, so the control in the Specification could not fail.** The Specification described the negative control as "temperature applied after top-k". Dividing by a positive temperature does not change the ranking, so that swap gives the same distribution and S-9 could never see it. Writing the test showed it; the implemented fault applies top-p before temperature, which does change the result.
- **A negative control's strength depends on the prompt.** The inverted penalty moves the distribution by 0.85 on `thai-medium` and by only 7.7e-3 on `english-short`, where the repeated tokens carry little probability. A tolerance of 1e-2 would have missed it there. The controls run on `thai-medium`, and the tolerance of 1e-5 catches even the weak case.
- **A test that passes against a stub proves nothing, and a mutation found a weak one.** The first penalty test passed even when the prompt was left out of the penalty's context, because the generated tokens alone made it pass. It was replaced by one built on a prompt whose best next token repeats the prompt, and four mutations (ignoring top-k, the seed, the prompt, the generated tokens) now each fail a test. Five of the S-9 tests had also failed for the wrong reason because tests sharing a temporary directory overwrote each other's files, which two mutations of the harness showed.
- **The cutoff exemption was not needed.** The draft Specification would have reported and not judged a setting whose top-k or top-p cutoff the engine's rounding could cross. The measurement showed the engine's error at the position S-9 uses is far smaller than the 3.5e-4 worst case of the earlier tables (which occurs at other positions), and no cutoff is near it. The owner decided to judge every setting and keep the margins reported.
- **Top-p is the expensive control**, because it sorts all 49152 probabilities each step: 934 us, 11% of a forward step. Applying top-k first leaves 40 tokens and the combined setting costs 562 us. A partial selection would make it cheaper; that is a separate technique and was not part of this release.
- **The long-workload gap to 0.1.1 is stable.** 0.1.2's long-workload generation was 5% above 0.1.1's with identical code and no explanation. 0.2.0, with different code, reproduces 0.1.2's figure to the third decimal (83.81 tokens/s), so one session's noise does not explain the gap; the cause is still unknown.

## Negative results

- **S-10 cannot see the order a sampler walks the tokens.** Walking them in reverse is a valid sampler with the same distribution. Replay is tested separately (FR-28), but a change of that order would change every seed's output without failing S-10.
- **The combined setting is a single token on two prompts** (`code-rust` and `long-go`), so on those prompts it cannot show a swapped order. The controls use a prompt where it keeps 7 tokens; a wider combined setting was considered and not added.
- **Sampling is checked at each prompt's last position only.** The penalty's context of generated tokens is tested through generation (a run under a penalty of 50 never repeats a token), not against the oracle's distribution, which uses the prompt alone.
- **Not measured: another machine.** S-9's tolerance rests on one machine; fixtures regenerated elsewhere are untested, as in 0.1.2.
- **No explanation for the long-workload gap to 0.1.1** (above).
- **The cost of top-p was measured and left.** It is recorded so a later release can decide.

## What comes next

The next release is 0.3.0, chat: the instruct variant of the model, its template and its stop conditions, as the owner decided on 2026-11-08 (sampling stays on the base model until then). It is not yet planned in the Requirements. At that bump the owner also decides whether the oracle stays a gate for later features (Requirements §13): this release's checks are the first that do not rely on matching the library's tokens. After chat, the roadmap's next version is batched prefill.
