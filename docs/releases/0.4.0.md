# Emberly Oxygen 0.4.0 — Release note

Nov 10, 2026 · @Wattanit

**One technique: batched prefill.** The engine now processes a prompt in one pass over all its positions, instead of feeding it one token at a time. The output is the same, and the prompt takes 22% to 26% less time at every length from 32 to 644 tokens. Built against Requirements 0.8 and Technical Specification 0.6 (both approved on 2026-11-10).

## What changed

- **A batched prompt pass** (FR-40). `Session::prefill` takes all the prompt's tokens, runs every layer over all positions together, leaves the same keys and values in the cache that one-token processing would, and returns the logits of the last position (or of every position, `Logits::All`, which only the harness asks for). Each position attends to itself and the positions before it, and to none after: the mask is a position count handed to the existing attention function, not a matrix. Decoding after the prompt is the one-token `step`, unchanged.
- **Only the last position's scores are computed.** The one-token path computed the 49152-way output projection after every prompt token and used only the last. Generation and chat now ask for the last position only.
- **A matrix-matrix product** (`matmul`, FR-40). Weight row outermost, input rows innermost, calling the same 16-partial-sum dot product as the matrix-vector product, which was moved into one function both call. It is safe, single-threaded and untiled, so this release measures batching and no other technique.
- **Generation, sampling and chat start from `prefill`.** `generate`, `generate_with` and a chat turn call it, so all three got the speed-up with no change of their own.
- **Logging follows** (Specification §14). At debug the prompt gives one `prefill` event (its size, the top candidates, its time, the first token chosen and, when sampling, that token's probability) and decode steps carry their real positions; at trace the prefill gives one event per layer, describing the last row.
- **The harness judges the batched pass** (FR-41). The logits, intermediates and top-1 tokens of S-1 to S-3 now come from one `prefill` per prompt, with every threshold, the 64-bit reference and the near-tie rule unchanged. A new test also runs each prompt through both paths and fails if their logits differ by more than 1e-5.
- **A negative control for the new pass.** `UnmaskedAttention` makes every position attend to the whole prompt, as a missing causal mask would. The harness fails on it at position 0 and names layer 0 as the first wrong tensor; the three older faults fail through `prefill` as before.
- **A prefill group in the benchmark** (FR-42). It times the prompt alone, up to the last position's logits, at 32, 67, 128, 512 and 644 tokens (the last two are the first and last turn of 0.3.0's ten-turn chat), as one step per token and as one `prefill`, in one process, and refuses to record anything unless the two agree on the last logits.
- **The test suite grew by 32 tests**: **420 tests** now run in about 41 s of test time.

## Why it was expected to help

The roadmap's v3: a prompt is known in advance, so its positions do not have to be processed one after another. Batching should let each weight be read once for the whole prompt instead of once per token, and the output projection, the largest single matrix, only has to be computed once. Chat made the cost visible: 0.3.0 took 6.5 s to the first token of a reply at 644 tokens of history.

## What was measured

Apple M4 Max, commit `7d4cde5` for the benchmark (clean tree, version 0.4.0, straight after `cargo test` passed, 420 tests). A first benchmark run was abandoned because the laptop slept during it, and the record is from a rerun with the machine kept awake.

**The output is the same.** On all 12 prompts, at every position (2,508 in all), the batched pass and the one-token pass are bit-identical in every logit, every layer's output and the greedy token. Every category passes S-1 to S-4, S-9, S-10 and S-11 with the same worst errors as 0.3.0: 3.50e-4 in logits (35% of S-1) and 9.97e-6 relative in intermediates (10% of S-2). The ids of 30 runs recorded before the change (greedy and seeded generation on all 12 prompts, and greedy and seeded chat over three turns) are identical after it. Bit-identity is a measured result, not a promise (FR-41 allows the last bits to move).

**The prompt takes less time at every length** (prompt time to the last position's logits, milliseconds, medians of 5 runs, both paths in one process):

| Prompt tokens | One step per token | One batched pass | Speed-up | Time saved |
| --- | --- | --- | --- | --- |
| 32 | 254.6 | 188.4 | 1.35× | 26.0% |
| 67 | 541.5 | 424.8 | 1.27× | 21.6% |
| 128 | 1060.1 | 806.8 | 1.31× | 23.9% |
| 512 | 4950.7 | 3727.9 | 1.33× | 24.7% |
| 644 | 6550.2 | 4928.1 | 1.33× | 24.8% |

**A chat turn is faster, and still grows with the conversation.** The first and last turn of the ten-turn chat of the 0.3.0 note take **0.55 s to 0.42 s** at 67 prompt tokens and **6.5 s to 4.9 s** at 644. Each turn still processes the whole history.

**The two workloads against 0.3.0's rows** (medians): the short prompt's throughput 121.2 → **169.2 tok/s (+39.6%)** and time to first token 264.1 → **189.1 ms (-28.4%)**; the long prompt's 100.3 → **137.2 tok/s (+36.8%)** and 5104.9 → **3730.7 ms (-26.9%)**. Generation throughput, which this release did not touch, reads 116.2 → 115.2 tok/s (-0.9%) and 79.7 → 82.0 tok/s (+2.9%), inside the 3% to 4% a session swings by; no change is claimed. Peak memory is 811.6 MB, as before.

## What was learned

- **The batching loop itself gave nothing in isolation, and the speed-up was not traced to its sources.** The matrix-matrix product is 1.00× against calling the matrix-vector product once per input, at the four per-layer shapes (60.8 ms against 61.0 ms for 506 inputs), at about 37 GFLOP/s, compute-bound; each weight matrix is 0.4 to 3.5 MB, and the repetition keeps it warm in the cache. A dry run before the release, at 506 tokens, estimated that about 17% of the one-token time came from computing the output projection once. The other 8% or so is unattributed: it may be weight reuse across tokens, which the isolated test cannot show (in the real pass all 540 MB of weights are read between two uses of one matrix), or removed per-step overhead. The release's rows show 22% to 26% in all.
- **The output projection was 17% of a token's work, not the "about a fifth" the Specification said.** 1.6 ms of a 9.7 ms step. It was recorded as feedback and written into the Specification in place, with the owner's permission.
- **A fault that only the batched pass sees showed the harness was not yet judging it.** The `UnmaskedAttention` control was written first and passed under the old harness, which still fed tokens one at a time. Only after the harness went through `prefill` did it fail, so the control did the job of a test of the harness's wiring.
- **A negative control needs a model that can show the fault.** At the forward tests' tiny model's head dimension of 2, interleaved and half-split rotary pairings are the same pairing, so the interleaved-RoPE fault changes nothing there; its check uses a model with head dimension 4.
- **A benchmark run is lost if the machine sleeps.** The first run was thrown away and repeated with `caffeinate`; nothing from it was recorded.
- **The in-process sweep is its own A/B.** Both paths run in the same process and session, so the 3% to 5% session swing seen in 0.2.0 and 0.3.0 does not touch the comparison.

## Negative results

- **The batching loop alone gives no speed-up in isolation** (above), and which part of the end-to-end gain is batching was not separated: the sweep compares 0.4.0 with 0.3.0 directly, by the owner's decision. More from batching needs a faster kernel, which is later work (Requirements §2.2): register blocking, SIMD or threads.
- **Attention is not batched.** By the dry-run estimate, about 20% of a long prefill (0.74 s of 3.69 s at 506 tokens, with the projections taking the rest) is attention and the small operations, and it still runs one position at a time, with the cost growing with the square of the prompt.
- **The saving does not grow with the prompt.** It is a steady 22% to 26% from 32 to 644 tokens.
- **A long chat is still slow.** Every turn processes the whole conversation (FR-35), so 4.9 s before the first word at 644 tokens of history is the number that a cache kept across turns would change.
- **Not measured: another machine.** As in earlier releases, the rows rest on one machine, and bit-identity between the two paths on one machine says nothing about another.
- **Bit-identity rests on this loop order.** FR-41 does not promise it; a faster kernel that changes the order of additions would give it up.

## What comes next

The next steps in the roadmap are a faster kernel (v4: register blocking, SIMD, threads, each measured on its own), which is where batching would start to pay for itself, and reusing the cache across chat turns, which would make a turn cost only its new tokens. Neither is planned in the Requirements (§2.2); the owner decides which is next and when.
