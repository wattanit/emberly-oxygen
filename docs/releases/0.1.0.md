# Emberly Oxygen 0.1.0 — Release note

Nov 6, 2026 · @Wattanit

**The baseline.** 0.1.0 is the first release, so there is no earlier release to compare with: it is the starting point every later release is measured against. Built against Requirements 0.1 and Technical Specification 0.1; the detailed record is the [implementation plan](../emberly-oxygen-implementation-plan-0.1.0.md) (§8 measurements, §9 findings) and the per-phase to-dos in [`docs/todo/`](../todo/).

## What this release is

A decoder-only inference engine for **SmolLM2-135M**, written from scratch in Rust and built by the book:

- **f32 throughout, one thread, no `unsafe`.** Every kernel is a plain loop, and every dot product adds in index order (Spec §4). The bf16 weights are widened to f32 exactly at load.
- **One token at a time.** The prompt goes through the same single-token forward pass as generation, with a key-value cache so each step computes only its own row (Spec §2).
- **A tokenizer written from the published file:** byte-level BPE with special tokens, a pre-tokenizer whose character classes were measured from the reference rather than taken from Rust's Unicode tables, and a streaming decoder that never emits half a character.
- **Greedy generation** with streamed text, request checks before any work, and an end-of-sequence token that stops generation without being printed.
- **A command-line tool,** `emberly-oxygen generate`, with `--stats`, three verbosity levels through `tracing` (each event placed in its `generate` → `step` → `layer` span), and `--log-file`.
- **A benchmark harness,** `cargo bench`, that writes every result with its conditions to `results/benchmarks.jsonl`.

## Why it was expected to work, and how we know it does

Nothing in the engine was trusted until a test it could fail said so.

- **An independent reference.** A pinned Python oracle (Hugging Face `transformers`, f32, CPU) stores logits, every layer's output and greedy continuations for 12 prompts in five categories: English, Thai, code, characters split across tokens, and 500-token texts. It is the only Python in the project.
- **The harness was seen to fail first.** It ran against a stub engine and failed every check before any engine code existed, and three deliberate faults (a wrong RoPE pairing, a 2e-3 perturbation of one logit, a dropped final norm) each make it fail where they should.
- **Measured agreement, every prompt, every category:**

  | Check | Threshold | Worst measured |
  | --- | --- | --- |
  | Logits, every position (S-1) | 1e-3 absolute | 2.36e-4 (Thai) |
  | Every intermediate tensor (S-2) | 1e-4 relative | 5.91e-6 (code) |
  | Top token, every position (S-3) | equal except at near-ties | passes at every position |
  | Greedy continuations, 32 tokens (S-4) | token for token | identical, no near-tie reached |

- **Reproducible:** repeated runs, and runs on a second load of the model, give bit-identical logits (S-6). The worst errors above came out identical to the last digit on two machines (an Apple M5 and the Apple M4 Max), with fixtures regenerated on each.
- **Logging changes nothing:** output is byte-identical at every verbosity level (S-8), and with no subscriber the logging costs nothing measurable (49.25 ms per step before it was added, 49.29 to 49.32 after).

`cargo test` runs all of this, 203 tests, in about 85 seconds.

## What was measured

On the benchmark machine (Apple M4 Max, 16 cores, 128 GB, macOS 26.3), at commit `0b4a5f3`, right after `cargo test` passed. Median of 5 runs after a warm-up, with the range:

| Workload | Time to first token | Prompt | Generation | Peak memory |
| --- | --- | --- | --- | --- |
| short: 32-token prompt, 128 generated | 1.68 s (1.66 to 1.71) | 19.0 tokens/s | 19.0 tokens/s (18.7 to 19.1) | 812 MB |
| long: 512-token prompt, 128 generated | 26.5 s (26.3 to 26.8) | 19.3 tokens/s | 18.5 tokens/s (18.3 to 18.6) | 812 MB |

Model load: about 60 ms. The kernel group times the engine's matrix-vector product against `matrixmultiply` (single-threaded) at the model's five matrix shapes: ours runs at 4.6 to 5.8 GFLOP/s, the library at 7.0 to 7.2, except on the 49152×576 output projection, where ours is faster (5.35 against 4.30).

These rows were taken while the machine was still warm from the test suite, and come out about 6% below runs on an idle machine (20.3 generation tokens/s on the short workload). They are kept as the baseline because they follow the release procedure as written; later releases follow the same procedure.

## What was learned

- **The matrix-vector product is the engine.** Per token, the timed products add up to about 48.6 ms of a 49.3 ms step, about 98.6%. Every other operation together (attention, norms, RoPE, the argmax) is the remaining 1.4%. Speed work that does not touch this kernel cannot matter much.
- **Prompts cost as much per token as generation.** Prompt and generation throughput are both about 19 tokens/s, because each prompt token is its own full forward pass. A 512-token prompt waits 26 seconds for its first token. Processing the prompt in batches is the obvious lever (roadmap v3).
- **Index-order addition is the main brake on the kernel.** Measured in Phase 4 and kept by the owner's choice for this release: the same loop with 4 independent partial sums ran about 2× faster, and with 8 about 5×, and is expected to stay inside the tolerances, since the reference itself adds in a different order; it has not been run through the harness. Adopting it needs a Specification change to "in index order" (roadmap v4).
- **Peak memory is set by loading, not generating.** The 812 MB peak is the memory-mapped bf16 file (269 MB) plus its f32 copy (538 MB), both resident during load; the key-value cache for 640 positions is small by comparison.
- **The tokenizer hides traps.** SmolLM2's vocabulary has no entry for 21 of the 256 byte values, and the reference silently drops those bytes, so the engine must too for exact agreement. Rust's `char::is_alphabetic` disagrees with the reference's `\p{L}` on some Thai vowel signs; a deliberate swap made 557 of 3,979 corpus cases fail, which is why the character classes are measured from the reference instead.
- **The reference itself needed care.** The library's hidden states replace the last layer's raw output with the normalized one, so the oracle captures layer outputs with hooks instead. RoPE angles must be f32 like the reference's: computed in f64, a cosine at position 5000 differs from the reference's by 8.4e-5.
- **Test infrastructure can be flaky where the engine is not.** Per-test `tracing` subscribers on parallel test threads race in `tracing`'s callsite cache and silently lose events (about 1 run in 10). The tests now share one global subscriber, with no failures in 1,000 runs.

## Negative results

- **`matrixmultiply` is a weak yardstick for this kernel.** HC-2 compares the in-house product with a mature library, but `matrixmultiply` is built for matrix-matrix products. With one column it is only about 1.25× faster than the plain loop at most shapes, and slower at the largest, because it repacks the matrix on every call. The Phase 4 partial-sum variants already beat it. The comparison is kept as specified, but it does not show how fast this kernel could be; plan §9 suggests a better reference for the Specification.
- **The benchmark is sensitive to the test run before it.** Running `cargo bench` straight after `cargo test`, as the Specification orders, left the workloads about 6% slower than on an idle machine. A fixed cool-down was considered and not adopted; the effect is recorded so that later comparisons account for it.
- **None of the 12 fixture prompts stops at the end-of-sequence token, and none reaches a near-tie,** so the harness never exercises either path end to end. Both are covered by unit tests on purpose-built tiny models instead.

## What comes next

Later releases each introduce one technique and are measured against these rows. The findings above point at batched prompt processing (roadmap v3) and CPU performance work on the matrix-vector product (roadmap v4); the roadmap's next version is sampling and chat (v2).
